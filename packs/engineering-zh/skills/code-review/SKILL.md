# 代码审查

审查的是**一段区间内的改动**，不是整个仓库。先把区间钉住，再分两轴审。

## 第一步：钉住固定点

固定点是这次审查的起点。给了提交号、标签或分支名，那就是固定点。只说「审查我的分支」，用分支的合并基点。只说「审查刚才的改动」，用工作区未提交的改动、`HEAD` 当固定点。说不上来就问一次，把候选列出来让它挑。

钉住之后列出改动清单：改了哪些文件、增删多少行、有没有重命名或删除。清单进报告，让读者知道审查覆盖了什么。范围里的格式重排、锁文件、生成产物单独点出来，别让它们淹没真正的改动。

完成标准：能一句话说出「审查区间是 A..B，涉及 N 个文件」。

## 第二步：两轴并行，各自独立

用 `subagent` 工具在**同一条消息里**发起两个子代理，各拿区间、改动清单和它那一轴的全部说明，各写各的结论。

两份输入必须分开喂：**规范轴的子代理看不到票据，规格轴的子代理看不到编码规范**。这是硬要求。规格轴一旦知道「这行违反了哪条规范」，就会顺手把不规范也算进「没实现好」；规范轴一旦读了票据，就会把票里没提的坏味道说成「偏离需求」。一条轴的结论漏进另一条，你拿到的就是一份被污染的判断，却还以为它是两份证据。

发完就等，别自己先猜结论。完成标准：两份结论都到手，各自都能独立站住。

## 第三步：规范轴

问的是：**这次改动有没有违反这个仓库自己写下来的编码规范？**

先找规范写在哪——项目说明文件、贡献指南、代码风格文档、周边同类模块的既有写法。找到就逐条对照。

仓库没写的地方，用这份通用坏味道清单兜底。这些是**给人判断用的提示**，不是硬性违规，也不自动判死：

- 同一段逻辑在两个以上地方重复出现。
- 名字看不出在干什么，或者名字和实际做的事对不上。
- 一处改动逼着改很多文件——影响半径超出这次改动该有的样子。
- 一个模块因为好几个互不相干的原因被修改。
- 为将来预留的抽象：只有一个使用者的钩子、参数、分支或基类。

每条命中给位置和理由；命中多条就分开写。仓库自己的规范**优先于**这份清单；两者冲突时按仓库的来，并说明你按哪条判的。清单里找不出问题就照直说，别为凑数把正常写法说成坏味道。

完成标准：每条结论都能指到具体位置，并说清它是违反了哪条写下来的规范，还是命中了清单里第几条。

## 第四步：规格轴

问的是：**这次改动是不是忠实实现了它对应的票据或规格？**

票据和规格在 `docs/agents/tickets/` 下，一个文件一张。按改动涉及的模块或编号找到对应那份；找不到就问用户要一次。确实没有来源，就记成「无对应票据」并说明——不要拿改动现状倒推出一份需求来。

逐项核对规格：要求做的，哪项漏了或只做半截；改动里多出来的功能、参数、分支、重构，一律挑出来，这是自作主张；行为边界对不对得上，包括报错、边界情况、默认值。

依据是规格文本，不是改动的样子。改得再干净，规格没要求就是多做；改得再丑，规格要求的都实现了就不算失职——丑不丑是规范轴的事。

完成标准：规格每一项都能标上「做了 / 没做 / 做过头了」，并指到具体位置或明确指出找不到对应实现。

## 第五步：并排汇报

两轴各占一栏，原文照放，**不合并、不排序、不互相补充**。不写「总体评价不错，但……」这类总结句，也不替用户换算成「通过 / 不通过」。两栏之间不交叉引用。每栏内部可以按严重程度排，两栏之间不做轻重比较。

交付写清三件事：审查区间、两轴各自的结论、你没查到的部分（缺票据、某类文件没看）。

规范轴需要兜底清单时读同目录的 `SMELLS.md`：十二类坏味道，每条给出怎么认出来、怎么修、严重度。
