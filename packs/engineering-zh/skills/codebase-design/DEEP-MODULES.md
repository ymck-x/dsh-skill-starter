# 深模块设计附件：词汇、度量与判断标准

正文（`SKILL.md`）只给流程，这份附件承载词汇、可数的指标和判断标准。数不清就先数，数清了再谈取舍。

## 一、词汇表

一次讨论里只用一个词对应一个含义。换词就是换了对象，讨论立刻失真。

| 词 | 一句定义 | 避免用哪些同义词 |
|---|---|---|
| 模块（module） | 任何有接口和实现之分的单位，可以是一个类、一个函数、一个包、一个进程 | 组件、服务、层、子系统——「服务」暗示进程边界，「层」暗示只能上下调用 |
| 接口（interface） | 调用方为了用对模块必须知道的全部事实：名字、参数、返回值、异常、调用顺序、不变量 | API、签名、契约——「签名」只覆盖一半事实，会漏掉顺序和异常 |
| 实现（implementation） | 接口背后的一切，调用方看不见也不需要知道 | 内部、细节、后端——「后端」暗示部署位置 |
| 深度（depth） | 藏在接口后面的行为量，相对接口尺寸的比值 | 抽象层次、复杂度、粒度——「抽象层次」不可数 |
| 缝（seam） | 不修改这段代码就能替换掉某个行为的位置 | 接口点、接入点、切面、边界——「边界」还指业务边界，会撞车 |
| 适配器（adapter） | 占住缝的一份实现，用来把真实依赖换成可控版本 | mock、桩、替身——「mock」还指工具和库，谈设计时一律说适配器 |
| 回报（leverage） | 一次改动能解决的调用方数量，乘以节省的调用方代码行数 | 复用、收益、效率——「复用」是手段，回报是这笔账的数额 |
| 局部性（locality） | 一个改动只落在一个模块和它的测试里的程度 | 内聚、解耦、边界清晰——都是形容词，换成「这次改动碰到几个文件」 |

## 二、怎么量深度

按顺序数三个数，填进同一张表。形容词不算结论，数字才算。

1. **接口宽度**：公开入口的个数，加上每个入口的参数个数，再加上调用方必须记住的顺序与不变量条数。三项相加就是宽度。
2. **隐藏量**：接口背后实现的行数，以及其中独立分支的条数。分支比行数更接近行为量，两者都记。
3. **记忆负担**：写通一次最常见调用所需的最少行数，以及为了用对它、调用方必须记住的事实条数。

把深度记成 `隐藏量 ÷ （接口宽度 + 记忆负担）`。经验阈值：

| 比值 | 判断 | 下一步 |
|---|---|---|
| ≥ 3 | 深模块，值得保留 | 记录它的回报，作为同类模块的模板 |
| 1 到 3 | 偏浅但可用 | 先合并入口、补默认值，再看比值 |
| < 1 | 浅模块，是拼装层 | 把常见路径收进模块，或把它并入调用方 |

判断信号：常见调用超过三行、接口宽度里有三条以上是「调用方必须自己保证」的、实现分支数少于入口数——出现任意一条就判浅。

完成标准：三个数落在表里，比值算出来，被判浅的模块写出要合并的具体入口名。

## 三、删除测试

对每个模块做一次假想删除，然后看复杂度去哪了。

1. 假设删掉这个模块，把它的行为按原样摊到调用点上。
2. 数需要改动的调用方个数 N，以及每个调用方要新增的行数。
3. 判断复杂度性质：如果能力整体消失、没有别处需要补上，说明复杂度被这个模块吃掉了，它是真的深；如果它在 N 个调用方里重新长出来，说明它只是把复杂度搬了个家，是浅模块。

判断信号：N 越大、每个调用方要补的行越多，模块越浅；某个调用方补出的代码恰好只有一行，说明它的入口本来就该是那个模块的默认行为。

完成标准：写出 N 的具体数字和每个调用点要补的行为，再决定保留、加深，还是把该模块并入唯一调用方。

## 四、缝的纪律

适配器的数量就是缝的验证方式，用数量说话。

- 一个适配器只证明存在一条**假想的缝**：你在纸上给依赖留了位置，但只有一份实现占着它。这时你无法确定缝的位置对不对——真实依赖的形状可能被这一份实现带偏，接口可能只是把库的调用样式抄了一遍。
- 两个适配器才证明存在**真实的缝**：语法不同、行为不同、边界条件不同的两份实现都能挂上去，说明接口描述的是需求，而不是某一份实现的影子。
- 因此纪律是：**缝上至少放两个适配器，再宣布这条缝成立。** 第二个适配器最便宜的来源是内存版（in-memory）、进程内假存储、或者把时钟和随机源做成可替换值。

判断信号：写完第一个适配器后接口还在随实现改动，说明缝是假想的；第二个适配器需要改动接口本身，说明接口描述的是实现而不是需求。

完成标准：每条被写进设计的缝都列出至少两份实现，并注明它们在哪一处行为上不同。

## 五、依赖的四种类型与测试策略

按依赖的性质分四类，每类配一种测试力度。先分类，再写测试。

| 类型 | 例子 | 测试策略 | 强度 |
|---|---|---|---|
| 进程内依赖（in-process） | 同进程的类、函数、模块 | 直接用真实现，不替换；先设计出深模块，再决定要不要替换 | 最高，能用真的就用真的 |
| 本地可替换依赖（local-substitutable） | 文件系统、数据库、时钟 | 用真货跑，或换内存与临时目录实现；必须测试两份实现行为一致 | 高，优先真货，其次内存版 |
| 远程但自有（remote-owned） | 内部 HTTP 服务、消息队列 | 在缝上放一个本地假实现做行为测试，另加一份**契约测试（contract test）**单独跑，保证假实现和真服务一致 | 中，行为测试用假的，契约用真的 |
| 外部不受控（external-uncontrolled） | 第三方 API、支付、邮件、随机源、系统时钟 | 注入端口并用适配器替换，测试里固定住返回值；把这类依赖全部推到边界，别让它渗进核心行为 | 低，只测「如何用」，不测「它给什么」 |

执行顺序：先列依赖清单，每个依赖标记类型；只对后两类建适配器；本地可替换类至少留一条用真货跑的通路。

判断信号：核心行为测试里出现网络或真实时钟，说明边界没收干净；契约测试与行为测试混在一个文件里，说明远程自有依赖的缝没定清。

完成标准：每个依赖有类型标签，每个适配器能说出它属于哪一类，远程自有依赖有两组测试分别覆盖行为与契约。

## 六、设计两次

同一份约束，交给三个以上子代理各自独立设计接口，再对比。用 `subagent` 工具在同一条消息里发起，每个子代理只拿一条约束，看不到彼此方案。

给每个子代理的输入：当前模块职责、真实调用方的代码片段、它要优化的那一条约束（例如：调用方最少行数 / 最容易测试 / 最容易加第二种实现 / 最容易并行改动）。要求它返回接口入口清单、每个入口的参数与返回、隐藏量的估计、它把缝留在哪里、以及一条最典型调用。

汇总后按同一张表对比，逐项给数字：

| 对比项 | 怎么算 |
|---|---|
| 深度 | 各自的 `隐藏量 ÷ （接口宽度 + 记忆负担）` |
| 局部性 | 实现「加第二种实现」「改一处业务规则」时各碰到几个文件、几条测试 |
| 缝的位置 | 各方案把适配器放在哪一层，需要几个适配器才成立 |
| 调用方成本 | 最典型调用的行数，以及调用方要记住的事实条数 |
| 变更成本 | 换掉被替换依赖时，各方案要改多少调用点 |

给出推荐：选出在深度和局部性上同时不输、且缝位置能被两个适配器验证的那一个；其余方案里值得吸收的单点（例如某个默认值、某个合并后的入口）列成补充项。

判断信号：三个方案的最典型调用几乎相同，说明约束没分化，重发一轮；两个方案只在命名上不同，说明它们其实是同一个设计。

完成标准：对比表每个格子有数字，推荐方案写出一句话理由，并列出从落选方案吸收的补充项；落选方案保留在同一份记录里，供下一轮变更时复用。
