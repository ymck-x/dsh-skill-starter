# 结构体检

这是一次勘察，不是大扫除。产出是候选清单，交给用户挑；这一步里代码保持原样。

## 一、定范围

- 翻最近的提交记录，按改动频率排序，把注意力放在经常改动的地方。
- 没人动过的角落先放过——那里没有真实的改动压力，收益拿不到。
- 用户点名了方向（某个模块、某处反复出问题的地方）就按用户说的来，不用自己重挑。
- 范围大时，用 `subagent` 工具在同一条消息里按区域并行发起勘察，各自只回结论和证据。

**完成标准**：能用一句话说出这次覆盖了哪几块，以及依据的是哪一段提交历史。

## 二、找加深的机会

用 `skill` 工具加载技能 `codebase-design`，借它的深模块词表。

对范围内每一块问三个问题：

- 同一件事是不是在很多调用方各写了一遍？
- 某个模块的接口是不是比它兜住的行为还显眼——调用方得先知道内部细节才能用？
- 想验证这块行为，是不是必须穿过一长串调用才够得着？

值得记下来的形态是：接口小、兜住的行为多、影响半径看得清、缝落在能单独验证的地方。

**完成标准**：手上有若干候选，每个都能点出具体是哪几个调用方、哪一段行为。

## 三、写一份看得懂的报告

每个机会占一小段，写四件事：

1. 现在什么样
2. 问题在哪（谁会因此被绊住）
3. 加深之后什么样
4. 为什么值得

配上 ASCII 结构图或前后对比图，让图承担大部分说明，文字只做注脚。报告抬头写明：这是候选清单，本轮不含任何代码改动。

**完成标准**：不熟悉这块代码的人两分钟内能看懂每个机会。

## 四、停下，让用户挑

报告交出去就停住。把选择权留给用户，一次拎一个。

用户挑中之后，就那一个展开追问，一轮问一批，把此刻能定的问题一次问完：

- 新接口的边界划在哪，哪些东西明确留在外面
- 谁迁到新接口上，旧的走法什么时候可以撤掉
- 用哪条反馈回路证明这次加深是对的

问清楚再动手。

## 五、动手那一个

- 先跑出一条能对当前问题变红的反馈回路。
- 把缝定下来，用曳光弹穿透一次走到头。
- 再逐个调用方迁移，一次一步，每步验证过再走下一步。
- 结构变化大到值得留痕时，先落一份规格或票据再改。
