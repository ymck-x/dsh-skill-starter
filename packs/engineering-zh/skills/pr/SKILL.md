# 拉取请求正文

正文写给三类人：明天来审的人、三个月后 git blame 找到这里的人、以及半年后回滚这个改动的你自己。三段，缺一段就不算写完。

## 一、摘要：用图示说清这次改了什么

读者不欠你阅读时间。一段三百字的散文，他得在脑子里重新搭一遍结构；一张五行的小图，结构已经搭好了。图示的信息密度来自「结构可见」——谁调用谁、什么变成了什么，一眼就落位。

**挑最小的那种。** 只在图装不下的时候才升级到下一档，不要两档都上：

- 几行伪代码：行为语义变了，比如某个分支的判定条件
- 调用树或时序图：控制流的路径变了，比如多绕了一层或去掉了一层
- 组件树：谁渲染谁、谁持有谁变了
- 文件树：落点变了，新增、移动、删除的边界
- diff 片段：纯粹的重命名、搬移、格式调整，贴原文比解释便宜

选择标准只有一条：**新来的人看完这张图，能不能直接说出「所以以前是 A，现在是 B」**。说不出来就换一档。

写完配一到三句白描：做了什么，为什么现在做，之前为什么不这么做。不要写成心得体会。

**完成标准**：把摘要单独发给一个没参与的人，他复述的改动范围和你的实际 diff 一致。

## 二、证据：让输出自己说话

「我测过了」「应该没问题」不算证据，那是断言。证据是读者不用信你也能得出的结论——它自己会讲话。

**先给出改前的样子，再给改后的样子。** 顺序不能反：只贴改后，读者无从判断这到底修好了什么，还是本来就长这样。两边都贴，中间那点差别就是证据的全部。

按改动性质挑一种：

- 命令输出：故障命令从报错变成正常输出，贴前后两段原文
- 截图：界面改动的改前改后两张图，附路径，正文里能看见差异
- 测试结果：新加的用例从红变绿；顺手写清它是怎么变红的（先写了失败的用例）
- 数据：改前改后的数字、条数、耗时，标注是怎么量出来的

**完成标准**：正文里能找到一条命令或一个路径，读者照着跑一遍能复现出同样的差别。找不到就还没写完。

## 三、合并风险：表态，不要含糊

每个改动都要明说它是什么门：

- **单向门**：合并后难以回退——改了数据格式、动了对外契约、迁移了迁移不回去的历史数据、删了别处还在用的东西。写清回退要付什么代价。
- **双向门**：随时能 revert，一个提交就回去了。直接写「双向门」，别绕。

然后写**影响半径**：这个改动波及到哪些调用方、哪些数据、哪些下游；谁的构建会红；有没有需要同步改动的仓库或配置。半径写具体到名字，不要写「影响面较小」这种无法验证的说法。

**完成标准**：读者看完能回答两个问题——出事了我能不能一键退回去；退不回去的话，最坏会坏到什么程度。

## 收尾

三段齐了再开拉取请求。若其中某段确实无事可说（例如纯文档改动没有可退风险），用一句话写「双向门，无影响半径」占位，不要留空——留空读者会以为你忘了写。
