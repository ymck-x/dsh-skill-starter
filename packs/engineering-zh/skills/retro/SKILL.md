# 复盘（retro）

一次构建刚落地时跑。目标不是评价这次代码写得好不好，而是让**下一次**同样的活少走弯路。
结论落在工作环境上：脚本、检查、文档、约定、说明文件。代码本身留给别的手段。

## 什么时候跑

**就在这段会话的末尾跑，别攒着。** 上下文一丢，你只剩一个结论，找不回当时卡在哪一步、
哪句话被反复解释了三遍。刚合完、刚验完就是最好的时机。

要复盘的那段会话如果不在当前上下文里，先把它找回来再开始：翻提交记录、翻票据文件、
翻自己刚才的轨迹。看不到过程就别硬猜。

只做一次，做完就走。复盘不是新的一轮开发。

## 六个方向找候选

逐条过，每条都问自己「这里有东西可捞吗」。没有就跳过，不硬凑。

1. **导航线索**：找东西费劲吗？反复猜文件名、反复 grep 同一个词、点开五层目录才发现不对。
   缺的是地图，不是耐心。
2. **该自动化却没自动化的检查**：同一个东西你手动核了两遍以上，或者一个错犯第二次。
3. **编码规范**：哪些做法是你当场自己定的？当场定的就是没写下来的。
4. **给模型的说明文件（AGENTS.md）**：这次有没有一条事实，你是靠翻代码、翻历史、
   或者问用户才拿到的，而它本该写在项目说明里？
5. **反复解释的背景**：同一段背景你跟用户解释了两遍，或者用户跟你解释了两遍。
6. **没起作用的指令**：有没有哪条约定、哪句要求、哪个技能，写了但当时根本没有影响行为。

## 怎么判断该沉淀成什么

**机械性的、重复犯的错 → 一条确定性的检查。** 判据：一个脚本能判定它对不对，
不需要谁来「看情况」。这类东西写成检查——脚本、lint 规则、测试——跑一次就知道。
写在文档里靠人记住，等于没写。

**要判断力的地方 → 一条规范。** 判据：两个都懂行的人可能做出不同选择，而且都能说得通。
那就别做成检查（会误报，误报的检查很快被无视），写成一句能当依据的约定。

拿不准的时候按「错一次的成本」定：错了要花几分钟重来，就做检查；错了要返工半天，值得写规范。
两边都不沾的，先不写——攒着，等它再出现一次再决定。

## 输出

**按痛感排序，最痛的那条第一个说。** 痛感就是它这次让你多花了多少时间和多少来回。

每条包含三样：

- **症状**：这次具体卡在哪、多花了什么代价。用这件事当时的样子说，别抽象。
- **动作**：要改什么、改成什么。具体到另一个人照着就能做完——加一条什么检查、
  往项目说明里补哪一句、把哪个约定定下来。
- **验收**：下次怎么算这条生效了。比如「这类错不再出现第二次」，或者
  「新来的人（或新开的会话）不用问就能找对地方」。

数量控制在三条以内。捞出来的东西多于三条时，合并同类项，或者把最弱的丢掉——
复盘的产出多了就等于没有产出。

**每条只给一个动作。** 一条建议里塞三件事，落地时会一件都不做。

## 收尾

把最有价值的那条**当场做掉**：写进项目说明文件、加上那条检查、定下那条约定。
这次会话里就能改完的事，别留成建议。

改完之后说清改了哪几处。剩下没做的，明确说它们还挂着。
