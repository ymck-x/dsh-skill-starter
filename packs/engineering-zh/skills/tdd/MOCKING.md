# 什么时候用假替身（mock）

这份附件回答一个具体问题：眼前这个依赖，这条测试里要不要放替身（test double）。

照着走：先看它是不是系统边界，是边界才考虑替身；然后在替代方案里从最真的那档往下挑，挑得到就别写替身；一定要写，就只写边界上被用到的那几个方法。替身只活在测试里，不进生产代码。

## 一、只在系统边界上做替身

边界是「控制权不在你手上」的那一层。判断一个依赖算不算边界，问一句：这条路径跑起来时，有没有东西会跨出你的进程，或者取值不由你的代码决定。

| 边界 | 一句判断依据 |
|---|---|
| 外部 API、第三方服务 | 它的可用性、延迟、返回数据都由别人控制，你只能观察，不能保证 |
| 数据库 | 换一个空库同样能跑通这条路径吗——约束、事务、SQL 语义本身就是被验证的行为 |
| 时间与随机数 | 这个值会随时刻、机器或调用次数变吗——它会变，期望值就不可重现 |
| 文件系统 | 这条路径读写的位置在你控制之外，或者跑完会留下需要清理的残留 |

把它记成一句话：**跨出进程、或取值不由你定的，才算边界。** 同一进程里的其他模块不算，那些代码就在你手里。

## 二、让自己写的类跑真代码

替身只给边界用。对自己写的类用替身，代价是两件具体的事：

- **行为没变却一重构就红。** 替身把测试钉在「谁按什么顺序调了谁」上，改内部结构就换调用顺序，红灯和用户看到的行为无关。
- **测试变成实现的复述。** 期望值抄的是同一套内部假设，实现和期望一起错时两边一致，测试永远绿。

判断依据：这条断言在重构后是否仍然成立。只关心调用形状的断言不成立，关心出口结果的断言成立。

做法：让自己的类用真对象跑；跑得慢就说明缝选错了，或者该给这层加一个内存实现——那是实现问题，不是测试问题。

## 三、能不用替身就不用：替代方案优先级

从第一档开始往下挑，挑到能跑通的那档就停。顺序按「保留了多少真实现的行为」排。

1. **真数据库加事务回滚。** 每条测试开一个事务，跑完回滚；用真的引擎、真的约束、真的 SQL。跳过的唯一理由是这条路会真的提交（外部系统、消息投递），那属于下一个边界。
2. **可注入的假时钟、假随机源。** 把不确定性变成入参：`now: () => new Date('2024-01-01T00:00:00Z')`。生产代码默认取真时钟，测试传假的。别用 sleep 等时间。
3. **内存文件系统或临时目录。** 用真的文件 API，只换存储位置：内存文件系统，或每条测试一个用完就删的临时目录。这样路径拼接、编码、权限这些行为仍然是真代码在跑。
4. **契约测试。** 替身必须存在时，让它的行为由一份可共享的契约定义，并让同一份契约定期对着真服务跑一遍。契约绿了，替身与真实现的差异就不再是猜测。
5. **录制回放（record/replay）。** 真调用录一份，回放时重放。最省事也最容易过期：给录制物写清谁负责刷新、什么时候重录，别让它悄悄腐烂。

优先级往下走，测试离真实行为就远一档。停在能满足这条路径的最高档。

## 四、把代码设计成可替换的

替身好不好写，取决于接口长得怎么样。三件事让边界可替换：

- **依赖注入。** 依赖从构造参数或函数参数传入，不在内部直接 new、不读全局单例。完成标准：测试能传进不同实现，而生产代码不需要为测试单独开口子。
- **SDK 风格的接口：被动数据加少量方法。** 接口是「几个数据名词 + 三五个动词」，参数和返回都是数据，方法本身不带状态机。形状示意：

  ```ts
  interface PaymentGateway {
    charge(amount: Cents, token: Token): Promise<Receipt>
    refund(receiptId: string): Promise<void>
  }
  ```

  这样写替身只需回答两个问题，不需要在替身里重建一套状态流转。
- **把不可控的东西挤到边界。** 让边界那一层负责翻译：把外部的丑形状转成内部好用的形状，内部剩下的全是纯数据与纯逻辑。完成标准：一条测试里最多替身一个边界对象；要替三个以上，说明缝选错了，回到正文「先定缝」那一步重来。

## 五、面对一个依赖，按这个顺序决定

1. 写下这个依赖跨的边界是什么：网络、磁盘、时钟、随机源，还是别人控制的服务。写不出来就是自己的代码，用真的，结束。
2. 试试在测试里直接用真实现。跑得通、够快、不留残留，就用真的，结束。
3. 真实现慢或留残留，去找它自带的内存版、临时版、测试模式（内存数据库、临时目录、测试传输层）。用真的 API，只换存储或传输。
4. 它的取值不确定，就把取值变成入参：注入时钟、注入随机源、把响应作为参数传进去。
5. 它必须跨进程，且它的行为属于你关心的规格，就写契约测试，让替身只实现契约里用到的那部分，并让契约对着真服务跑。
6. 真服务在 CI 里跑不起来（要钱、要凭据、会抖），退到录制回放，同时写清刷新责任与重录时机。
7. 以上都不行才手写替身：只实现被调用的方法，只返回被断言用到的数据，行为保持诚实——真实现会拒绝的输入，替身也拒绝。

每一步停下来的标准都是同一条：这条路径在缝上有一条能跑、能红的测试。停下来就别再往下走一档。

## 六、替身用多了的信号

出现下面任何一条，说明测试已经开始和实现绑在一起，按对应的动作改：

- **一条测试里替身超过一个边界对象。** 缝选大了，收窄到这一个行为真正穿过的那一处。
- **改内部结构，行为没变，测试红了。** 断言落在调用形状上，改成从缝上断言出口结果。
- **为了测试给生产代码加参数、开放可见性或塞测试分支。** 依赖注入没做到位，把依赖挪到构造参数上。
- **替身里长出 if 分支和状态记录。** 你在替身里重建了实现，退回契约测试或改用真实现。
- **断言在比调用顺序、调用次数、参数逐字相等。** 换成断言返回值、之后可观察的状态、发出的副作用。
- **测试全绿，接上真环境就坏。** 替身与真实现的差异被当成了规格，补一份契约测试。
- **测试里出现 sleep、轮询等待、依赖执行顺序。** 时间或随机源没被注入，把它变成入参。

一条判据收尾：**把替身全删掉换成真实现，这条测试还应该讲同一个故事。** 讲不出来，被替身绑住的就不是边界，而是你自己的代码。
