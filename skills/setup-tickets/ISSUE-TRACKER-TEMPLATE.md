# 票据与规格的约定

本项目用本地 Markdown 文件记录要做的活，不使用在线工单系统。

## 放在哪

- 票据和规格都写进 `docs/agents/tickets/`，一个文件一条，文件名是 `<编号>-<短名>.md`。
- 编号从 1 开始，全局递增，不复用。删掉的编号作废。
- 绝不要把多条票据写在同一个文件里。

## 状态字段

每个文件正文最前面写一行状态，只能是这四个之一：

| 状态 | 含义 |
|---|---|
| `待确认` | 还没定，需要人拍板 |
| `已就绪` | 说清楚了，智能体可以直接领取开工 |
| `进行中` | 有人在做 |
| `已完成` | 做完了 |

## 依赖怎么写

用「阻塞于 #编号」表达。只有它列出的所有票据都到了 `已完成`，这张票据才算 `已就绪`。

没有任何阻塞的就写「无（可以立刻开始）」。

## 票据模板

```
# <编号>：<标题>

**状态：** 已就绪

**要构建什么：** 这张票据让什么行为端到端可用，从用户视角描述，不要写成逐层的实现清单。

**阻塞于：** 卡住它的票据编号与标题，或者「无（可以立刻开始）」。

**验收标准：**
- [ ] 标准一
- [ ] 标准二
```

## 规格模板

规格也放同一个目录，模板见 `to-spec` 技能。一份规格通常由 `to-tickets` 再拆成多张票据。

## 怎么推进

按**前沿（frontier）**走：所有阻塞者都已完成的那些票据，就是现在可以开工的。一条纯线性的链条就从第一张往下做。

## 写作要求

- 标题和描述用项目自己的词汇（见 `GLOSSARY.md`），不要自造词。
- 不要写具体文件路径和代码片段，它们过时得快。要表达决策时写决策本身。
- 例外：原型产出的状态机、schema、类型形状这类决策密集的片段可以内联，并注明它来自原型。
